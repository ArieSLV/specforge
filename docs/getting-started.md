# Getting started with specforge

specforge is a spec-driven development MCP server for AI-assisted .NET architecture work. This guide takes a new adopter from "never heard of specforge" to "first decision drafted, first item drafted, baseline validated".

specforge is consumed through an MCP-aware host (Claude Code or Codex CLI). You do not run it as a standalone CLI — the binary opens an MCP stdio loop and waits for a host to call its tools. Everything below is phrased as the tool calls your host makes on your behalf; when an Agent Skill is installed, the skill walks the same sequence for you.

## Before you start

Requirements:

- **Windows x64.** The MVP ships a `win-x64` self-contained binary only. Other platforms are out of MVP scope.
- **.NET SDK 10.0.201** (or a compatible 10.0.x feature band, per `global.json`). Needed only to build from source; the pre-built binary is self-contained.
- **An MCP-aware host.** Claude Code or Codex CLI. specforge registers once, user-wide, and is then available in every project the host opens.

Pre-conditions for a fresh bootstrap:

- No existing `.specforge.json` in the project you are bootstrapping. If one exists, you are upgrading, not bootstrapping — see [Upgrade ritual](#upgrade-ritual).

## Install specforge

specforge is distributed as a single self-contained executable. There are two ways to obtain it.

### Build from source

Clone the repository, then build and publish the MCP project to a stable output directory. Use PowerShell:

```powershell
git clone <repo-url> D:\Work\specforge
cd D:\Work\specforge
dotnet build Specforge.sln -c Release
dotnet publish src/Specforge.Mcp/Specforge.Mcp.csproj -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true -o D:\Work\specforge\bin\
```

This produces `D:\Work\specforge\bin\specforge.exe`. The output directory is deliberately framework-agnostic (`bin\` rather than the default `bin\Release\<tfm>\win-x64\publish\`) so the path you register with your host does not change when the target framework moves. Keep `<publish-dir>` at a fixed, known location — your host configuration references it by absolute path.

### Pre-built binary

Pull the release archive from `<release-url-placeholder>` (the release/publish pipeline is post-MVP; this placeholder stands in until it is set up) and extract it to your chosen `<publish-dir>`, for example `D:\Work\specforge\bin\`.

The binary does not expose a standalone command line. Running `specforge.exe` directly opens an MCP stdio loop and blocks waiting for a host — this is expected. Verify the install through your host instead: after [registering the server](#register-the-mcp-server), your host's tool list should show **21 specforge tools**.

## Register the MCP server

Register specforge **once, user-wide** — not per project.

### Claude Code

Add an entry to your user-scope `~/.claude/.mcp.json`:

```json
{
  "mcpServers": {
    "specforge": {
      "command": "D:\\Work\\specforge\\bin\\specforge.exe",
      "args": []
    }
  }
}
```

The server identifies the target package per tool call, not from launch arguments — so `args` stays empty.

### Codex CLI

Codex projects declare specforge as a project-level MCP dependency through `agents/openai.yaml`. specforge writes this file for you during `init` (see below); its content is:

```yaml
# Generated by specforge init. Declares specforge as a project-level MCP server for Codex.
mcp_servers:
  specforge:
    command: specforge
```

User-wide skills (the next section's `install_skills` output) land in `~/.agents/skills/` for Codex and `~/.claude/skills/` for Claude Code.

## Bootstrap a new project (the bootstrap quartet)

Four tool calls bring an empty repository to a known-clean baseline: `init` → `install_skills` → `use_package` → `validate`. The `adopt-existing-project` skill walks exactly this sequence and is the AI-facing counterpart to this section.

### 1. `init`

`init` writes the project's configuration and instruction layer. It **requires** a `packages` array; a typical first call also scaffolds the spec directory layout and writes all behavioral files:

```json
init {
  "packages": [{ "name": "my-app", "path": "spec/packages/my-app" }],
  "scaffold": true,
  "behavioralFiles": "all"
}
```

This writes:

- `.specforge.json` — the configuration, stamped with the current `schemaVersion`.
- `SPECFORGE.md` — project-level instructions with auto-generated standard sections (always overwritten on re-run).
- A tagged block in `CLAUDE.md` and a tagged block in `AGENTS.md` — only the specforge-owned block is edited; the rest of each file is left untouched.
- `agents/openai.yaml` — the Codex MCP-dependency declaration. `behavioralFiles` accepts `all | claude-only | codex-only | none`; this file is written for the `all` and Codex-only modes.
- A `spec/` scaffold with `decisions/`, `items/`, `ledger/`, `shared/`, and `templates/` directories — written when `scaffold` is `true`.

Preview before writing with `dryRun=true` — `init` reports `writtenPaths`, `overwrittenPaths`, and `skippedPaths` without touching the filesystem. The four project-level outputs are always `.specforge.json`, `SPECFORGE.md`, the `CLAUDE.md` block, and the `AGENTS.md` block; `agents/openai.yaml` is the optional fifth Codex-mode output.

### 2. `install_skills`

```json
install_skills { "agent": "all" }
```

This extracts the embedded SKILL.md bodies to the user-wide skill directories — `~/.claude/skills/<name>/SKILL.md` for Claude Code and `~/.agents/skills/<name>/SKILL.md` for Codex (`agent` accepts `claude-code | codex | all`). It is a one-time call per binary version; re-running after a binary upgrade refreshes the skill content, and reinstall is always-overwrite, so it is safe to repeat. Use `dryRun=true` to preview the target paths first.

### 3. `use_package`

```json
use_package { "name": "my-app" }
```

This sets the session's active package. Single-package projects auto-select on the first tool call, so this step can be skipped for them; multi-package projects must pick one. Call `list_packages` to enumerate the configured packages.

### 4. `validate`

```json
validate { "aspect": "all" }
```

This runs a read-only consistency check and returns a structured findings list (each finding carries a `severity` of error, warning, or info). The envelope is a success even when findings exist — findings are data, not failures. The goal for a clean baseline is `errorCount` equal to zero. The accepted aspects are `ids | links | lifecycle | impact-coverage | all`.

## Author your first decision

A decision record captures an architectural choice and its cross-cutting impact. Invoke the `draft-decision` skill through your host, or drive the tools directly:

1. `create_decision title="<Plain Title>"` allocates the next `DEC-NNN`, writes the record from the template, adds its artifact row, and appends a Created history event.
2. Iterate the body with your AI assistant. Use the `impact-assessment` skill to fill the Impact Assessment table thoroughly — that table is what makes a decision reviewable.
3. `set_decision_status id="DEC-NNN" status="Draft for user review"` when the draft is ready for a human.
4. `set_decision_status id="DEC-NNN" status="Approved" reviewer="<name>" notes="<summary>"` records approval and appends a review (`REV`) row.

The `review-decision` skill walks the reviewer side of this flow — what to check before approving.

## Author your first item

An item spec is an implementation-ready slice that hands off cleanly to a fresh AI session. It depends on the approved decisions that justify it. Invoke the `draft-item` skill, or drive the tools directly:

1. `create_item title="<Plain Title>" dependsOn=["DEC-001", "DEC-002"]` allocates the next `ITEM-NNN`, writes the spec from the template, adds its row to the item ledger, and appends a Created history event. The `dependsOn` list should name the approved decisions the item rests on.
2. Fill the required sections with your AI assistant — Handoff Summary, Target Behavior, Code Scope, Done Criteria, and the rest.
3. `set_item_status id="ITEM-NNN" status="Draft for user review"` to hand it to a human.
4. `set_item_status id="ITEM-NNN" status="Approved" reviewer="<name>" notes="<summary>"` to approve.

The `review-item` skill walks the reviewer side — confirming the Done Criteria are testable and the Code Scope is bounded.

## Validate the spec graph

Run `validate aspect=all` whenever you want a health check of the whole package. Invoke the `validate-spec-graph` skill for the fix recipes, or read the findings directly. Severities mean:

- **error** — a broken invariant (a dangling reference, an unreachable lifecycle state, an ID gap). Fix before relying on the graph.
- **warning** — a likely problem worth a look (for example, an approved item whose decision is still in draft).
- **info** — an observation, no action required.

Gate downstream work on `errorCount` equal to zero.

## Undo a mistaken creation

If you create a decision or item by accident during onboarding, remove it with the matching delete tool:

- `delete_decision id="DEC-NNN" confirm=true` tombstones the decision.
- `delete_item id="ITEM-NNN" confirm=true` tombstones the item.

Deletes require `confirm=true` and leave a tombstone so the ID is never silently reused. Review the change in git before moving on. (See the `validate-spec-graph` skill if a delete leaves a dangling reference behind.)

## Upgrade ritual

When a new specforge binary version ships, run this sequence against your existing repo:

1. **Re-build or re-download** the binary per [Install specforge](#install-specforge), replacing the executable at your `<publish-dir>`.
2. **Verify the version** with `info`. Confirm the reported `binaryVersion` and `supportedSchemaVersionRange` are what you expect.
3. **Preview** with `init dryRun=true` against the existing repo. Most config fields are immutable across a re-init; review the planned changes. The `.specforge.json` `schemaVersion` may upgrade in memory when the new binary supports a higher version.
4. **Apply** with a real `init`. The schema-upgrade chain runs in memory; the opportunistic write to `.specforge.json` fires the next time any tool writes to it. The always-overwrite files (`SPECFORGE.md`, the tagged blocks) are refreshed now.
5. **Review in git.** Commit the `init` changes before redeploying skills, so the instruction-layer diff is auditable on its own.
6. **Refresh skills** with `install_skills agent=all`. Always-overwrite means stale skill bodies are replaced with the new binary's versions.
7. **Confirm** with `validate aspect=all`. A clean `errorCount` of zero verifies the upgrade introduced no inconsistencies.

As of the current binary the supported range is `[1, 1]`, so the in-memory schema upgrade in steps 3–4 is a no-op — the ritual above is the procedure you will follow once a binary ships a higher `schemaVersion`. The always-overwrite refresh in steps 4 and 6 applies on every upgrade regardless. The `README.md` "Status" line is a manual edit; update it as part of this ritual when the project's stage changes.

## Where to learn more

- `spec/packages/specforge-mvp/decisions/` — every architecture decision (`DEC-NNN`) with its rationale and impact assessment.
- `spec/packages/specforge-mvp/items/` — every item spec (`ITEM-NNN`) with its implementation plan and Done Criteria.
- `spec/shared/` — the lifecycle policy, glossary, spec-item contract, and impact-assessment checklist shared across packages.
- `spec/skills/` — the authored SKILL.md bodies: `draft-decision`, `review-decision`, `draft-item`, `review-item`, `impact-assessment`, `validate-spec-graph`, and `adopt-existing-project`. These are the AI-facing counterparts to this guide.
- `README.md` — the repository entry point and quick start.
