# DEC-002-CONFIGURATION-AND-DISCOVERY - Configuration and Discovery

Supersedes: none

## Context

`DEC-001-DISTRIBUTION-AND-TRANSPORT` established that specforge runs as a per-session, host-spawned MCP server registered once user-wide, and that the server identifies the target package per tool call rather than at launch. It deliberately left the discovery mechanism to this record.

A target project may contain one or many spec packages (multi-package support is a confirmed requirement). The running server must:

- find the configuration that describes the project's spec layout;
- enumerate available packages;
- know which package is "active" for the current work;
- resolve shared material (glossary, lifecycle, impact checklist) and templates, including per-package overrides.

On 2026-05-25 the user chose, via structured questions:

- discovery by **config file** at the repo root, found by walking up from the working directory, generated by `init`;
- multi-package selection **by name, set once per session**, switchable via a tool;
- shared material **shared at the repo level with per-package override**.

This record formalizes those choices and fills in the mechanics.

## Decision

### Configuration File

specforge reads a JSON configuration file named `.specforge.json`.

- It lives at the project root, or any ancestor directory of the working directory.
- The server finds it by walking up from the host-provided working directory until the first `.specforge.json` is found.
- It is generated by the `init` tool, so it is not hand-authored in normal use.
- It carries `schemaVersion` for forward compatibility (full versioning policy is `DEC-006-SCHEMA-VERSIONING`).

### Configuration Schema (version 1)

```json
{
  "schemaVersion": 1,
  "shared": "spec/shared",
  "templates": "spec/templates",
  "packages": [
    { "name": "specforge-mvp", "path": "spec/packages/specforge-mvp" }
  ]
}
```

- All paths are relative to the directory containing `.specforge.json`.
- `packages` is an explicit list of `{ name, path }`. Explicit listing — rather than globbing `packages/*` — lets specforge adopt existing non-conforming layouts (for example RavenDB-26295's `artifacts/RavenDB-26295/specification/`) without forcing a restructure.
- `shared` and `templates` are the repo-level defaults applied to every package.
- The config carries no per-package override fields. Per-package override is by convention only (see "Shared and Templates Resolution" below).

### Discovery Flow

```text
host launches server, cwd = <somewhere in the project>
        |
        v
first tool call that needs a package
        |
        v
walk up from cwd for .specforge.json
   <cwd>                       no
   <cwd>/..                    no
   <project root>              .specforge.json FOUND
        |
        v
parse config -> packages, shared, templates
        |
        +-- exactly one package  -> auto-select it as active
        |
        +-- multiple packages    -> no active package yet;
        |                           package-requiring calls return a
        |                           selection error listing names
        |
        v
active package known for the rest of the session
```

If no `.specforge.json` is found, package-requiring tools return a clear error instructing the caller to run `init`. A missing config is never silently treated as an empty or default package.

### Package Selection

- Available packages come from the config `packages` list.
- The active package is held in the server process memory. Because `DEC-001` makes the server per-session, the active selection lasts for the session and is rebuilt on the next session.
- Selection is by **name** via a dedicated tool (working name `use_package`, finalized in `DEC-007-MVP-TOOL-SET`).
- Default behavior:
  - exactly one package in config -> auto-selected, no explicit call needed;
  - more than one -> the first package-requiring tool call without a prior selection returns a selection error listing the available names; the caller then calls `use_package`.
- The active package can be switched at any time with another `use_package` call.

### Shared and Templates Resolution

Resolution is **file-level override**, not merge:

```text
effective shared file  = <package shared>/<file>     if it exists
                         else <repo shared>/<file>

effective template     = <package templates>/<file>  if it exists
                         else <repo templates>/<file>
```

- The repo-level `shared` and `templates` paths are the base.
- A package overrides an individual file **by convention only**: if the package path contains a `shared/` or `templates/` subdirectory, files there override the repo-level files of the same name. No config field is involved. This keeps a single source of truth — the filesystem — and removes the risk of config/filesystem desync.
- Override is whole-file: if a package supplies its own `glossary.md`, that file is used in full for that package; the repo-level `glossary.md` is not merged in.

## Alternatives Considered

| Alternative | Rejection reason |
|---|---|
| Pure cwd auto-detect (no config) | Zero setup, but breaks when the host launches the server from an unexpected directory. The config-file approach keeps a deterministic anchor while still being found via cwd walk-up. |
| Explicit package path argument on every tool call | No setup and unambiguous, but verbose on every call and forces the AI to always know and supply the correct path. Session-scoped named selection is far less noisy. |
| Glob `packages/*` instead of an explicit package list | Convention-over-configuration is tidy for the greenfield specforge layout, but cannot adopt existing non-conforming layouts (e.g. RavenDB-26295's `specification/` folder) without a restructure. Explicit list is more portable; `init` writes it so there is no hand-maintenance. |
| Active package named on every call | Unambiguous but verbose. Session-scoped selection matches the reality of focusing on one ticket at a time. |
| Per-package fully self-contained shared/templates (no repo-level base) | More duplication of glossary/lifecycle across packages; drifts easily. Repo-level base with per-package override avoids duplication while preserving flexibility. |
| Merge shared files instead of whole-file override | Merging markdown is ambiguous and error-prone (which section wins?). Whole-file override is predictable and easy to reason about. |
| Persist active package to disk across sessions | Adds state files and staleness handling for little benefit; DEC-001's per-session model already discards process state cleanly. Re-selection per session is cheap. |

## Consequences

- Every target project needs one `.specforge.json` at its root, generated by `init`.
- The server is deterministic about which package it operates on; a missing config is a hard error, never a silent default.
- Adopting specforge for an existing project (e.g. RavenDB-26295) is a config-authoring task, not a directory restructure, because package paths are explicit.
- Multi-package repos require a `use_package` call when more than one package exists; single-package repos need none.
- Shared material lives once per repo and is overridden per package only where genuinely needed, reducing drift.
- The active-package selection is session-scoped; switching tickets mid-session is an explicit `use_package` call.
- `init` must be able to both generate a conforming layout and write a config pointing at an existing layout.

## Resolved During Review

- **Per-package override mechanism** — resolved 2026-05-25 as **convention-only**: a `shared/` or `templates/` subdirectory inside the package path overrides repo-level files; no config field. Simpler code path; no config/filesystem desync risk.
- **Default active package field** — resolved 2026-05-25 as **omitted from MVP**: re-selection per session is cheap; user works on one ticket at a time; single-package repos auto-select; adding a field for an edge case is not justified for the MVP.
